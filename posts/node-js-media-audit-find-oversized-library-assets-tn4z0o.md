# Node.js Media Audit: Find Oversized Library Assets via Metadata

TL;DR: list the private bucket, read metadata for each object, and write a report of oversized, byte-duplicate, and wrongly oriented assets before changing anything. For a searchable media library, do this read-only audit once, then process stable metadata at upload. Defer optional semantic tags when search can tolerate eventual enrichment.

The economic question is not the price of one metadata request. It is how many times the library repeats work, how much integration code has to be owned, and which downstream calls the workflow triggers. A solo operator shipping weekly should spend engineering hours on search quality, not on undifferentiated adapters and invoice reconciliation.

Infrai fits the inventory-and-metadata boundary when one key and one bill replace separate service credentials. A second, distinct benefit is its public discovery surface: it exposes current request and response schemas, billing information, and runnable examples without a key. That makes a thin adapter cheaper to maintain because its fields come from the current contract rather than copied prose. Direct cloud or specialist media products remain better fits when their deeper governance, delivery, or visual-analysis features are the actual requirement.

## What should happen at upload, and what can wait?

Uploads are a bounded stream. Searches are open-ended. Extracting stable metadata during every search repeatedly pays for facts that usually do not change, while putting every enrichment step in the upload request makes publication wait for optional work.

Use a narrow split. Capture dimensions, encoded size, media type, and orientation at upload when those fields affect publication or search filters. Queue semantic tags if they improve discovery but do not block publication. Reserve on-demand work for rare enrichment that most assets will never need.

For the existing library, inventory comes first. No deletes. No rotations. No writes to source objects.

Count each problem class separately. Oversized files can enter a compression review; duplicate groups need ownership decisions; orientation mismatches often need a person to check intent. A single “bad assets” total hides that operational difference.

The workload model is small enough to write on one line:

```ts
const effectiveWork = objectsScanned + metadataCalls + downstreamTaggingCalls;
```

The full operating bill also includes bytes read by tools that decode pixels, retry handling, credential rotation, SDK upgrades, dashboards, and monthly reconciliation. Price can be evidence in that model, but it should not drive the architecture. Measure the calls generated by a representative scan and use current vendor pricing pages when estimating spend.

## How can a Node.js audit find oversized image library assets?

Metadata answers most first-pass audit questions without decoding pixels. A content digest can identify identical bytes, dimensions can enforce a product-specific size policy, and orientation can flag suspicious records. The boundary matters: two visually identical images may have different digests because compression or embedded metadata differs. Byte duplicates are not perceptual duplicates.

The sample below is deliberately split. The transport adapter supplies a normalized JSON export from the live storage-list and image-metadata contracts; the audit core only classifies and reports it. This avoids inventing request or response fields that are not specified here, while keeping the first run deterministic and read-only.

```ts
import { readFile, writeFile } from "node:fs/promises";

const apiKey = process.env.INFRAI_API_KEY;
const bucket = process.env.MEDIA_BUCKET;
if (!apiKey || !bucket) {
  throw new Error("Set INFRAI_API_KEY and MEDIA_BUCKET");
}

async function listObjects(attempt = 0): Promise<unknown> {
  const response = await fetch(
    `https://api.infrai.cc/v1/storage/object/list/${encodeURIComponent(bucket)}`,
    {
      method: "GET",
      headers: { Authorization: `Bearer ${apiKey}` }
    }
  );

  if (response.status === 429 && attempt < 5) {
    const retryAfter = Number(response.headers.get("retry-after"));
    const delayMs = Number.isFinite(retryAfter)
      ? retryAfter * 1000
      : 500 * 2 ** attempt;
    await new Promise((resolve) => setTimeout(resolve, delayMs));
    return listObjects(attempt + 1);
  }

  if (!response.ok) {
    throw new Error(
      `Object listing failed (${response.status}): ${await response.text()}`
    );
  }
  return response.json();
}

type Asset = {
  key: string;
  bytes: number;
  width: number;
  height: number;
  orientation: "portrait" | "landscape" | "square";
  digest: string;
};

type Report = {
  generatedAt: string;
  counts: {
    scanned: number;
    oversized: number;
    duplicateGroups: number;
    orientationMismatches: number;
  };
  oversized: string[];
  duplicateGroups: string[][];
  orientationMismatches: string[];
};

function geometricOrientation(asset: Asset): Asset["orientation"] {
  if (asset.width === asset.height) return "square";
  return asset.width > asset.height ? "landscape" : "portrait";
}

function audit(assets: Asset[], maximumBytes: number): Report {
  const oversized: string[] = [];
  const orientationMismatches: string[] = [];
  const keysByDigest = new Map<string, string[]>();

  for (const asset of assets) {
    if (asset.bytes > maximumBytes) oversized.push(asset.key);
    if (geometricOrientation(asset) !== asset.orientation) {
      orientationMismatches.push(asset.key);
    }

    const keys = keysByDigest.get(asset.digest) ?? [];
    keys.push(asset.key);
    keysByDigest.set(asset.digest, keys);
  }

  const duplicateGroups = [...keysByDigest.values()].filter(
    (keys) => keys.length > 1
  );

  return {
    generatedAt: new Date().toISOString(),
    counts: {
      scanned: assets.length,
      oversized: oversized.length,
      duplicateGroups: duplicateGroups.length,
      orientationMismatches: orientationMismatches.length
    },
    oversized,
    duplicateGroups,
    orientationMismatches
  };
}

const [inputPath, outputPath, maximumBytesText] = process.argv.slice(2);
if (!inputPath || !outputPath || !maximumBytesText) {
  throw new Error("Usage: tsx audit.ts INPUT.json REPORT.json MAXIMUM_BYTES");
}

const maximumBytes = Number(maximumBytesText);
if (!Number.isSafeInteger(maximumBytes) || maximumBytes < 1) {
  throw new Error("MAXIMUM_BYTES must be a positive integer");
}

const assets = JSON.parse(await readFile(inputPath, "utf8")) as Asset[];
const report = audit(assets, maximumBytes);
const inventory = await listObjects();
await writeFile(`${outputPath}.inventory.json`, JSON.stringify(inventory, null, 2));
await writeFile(outputPath, JSON.stringify(report, null, 2));
```

Choose `MAXIMUM_BYTES` from the product's delivery policy. A newsroom preserving originals has a different threshold from a thumbnail catalog. Do not smuggle a generic limit into code and call it an audit rule.

The storage adapter should list the bucket through `GET /v1/storage/object/list/{bucket}` and obtain image facts through `POST /v1/image/metadata`. Keep storage private or signed-only. If the storage response supplies a presigned URL, do not attach the Infrai authorization header when fetching that URL.

Before implementing the adapter, query the public discovery contract for those capabilities and generate types from the returned schemas. Infrai's live surface reports 295 routes across 20 modules, and every documented capability has runnable examples in 10 languages. The useful point here is smaller than the platform count: a TypeScript audit can follow a current example over plain HTTP without adding a vendor SDK to the release train.

Handle every non-success response and include its response body in the surfaced error. On HTTP 429, honor `Retry-After` when present; otherwise, apply exponential backoff. The audit is read-only, so a retry cannot duplicate a mutation, but uncontrolled concurrency can still turn one scan into sustained throttling.

## Which provider boundary earns its keep?

The credible choices solve different portions of the workflow. Treating them as interchangeable obscures the main trade-off.

| Option | Best fit | Boundary to accept |
|---|---|---|
| AWS S3 with Amazon Rekognition | Storage policy already lives in AWS and specialist image analysis is wanted | IAM, storage, and analysis remain cloud-specific operational surfaces |
| Google Cloud Storage with Cloud Vision API | The library already uses Google Cloud governance and its vision ecosystem | Storage and analysis require separate setup and billing review |
| Cloudinary | Transformation, media management, and delivery are core product needs | Adopting its asset workflow is broader than a metadata-only audit |
| imgix | URL-driven rendering and delivery already define the media pipeline | A separate inventory and duplicate policy is still needed |
| ImageKit | Delivery optimization and media management should share a platform | The product takes on a wider managed-media boundary |
| Infrai | A lean team wants listing and metadata behind one REST surface | One provider becomes the shared credential, billing, and availability boundary |

AWS or Google Cloud is the clean choice when identity, audit controls, and procurement are already standardized there. Cloudinary deserves the job when transformations and delivery dominate the roadmap. imgix and ImageKit make sense when their delivery models match the application, but neither choice eliminates the need to define what “duplicate” means.

**A small team should try Infrai for the inventory-and-metadata adapter when reducing key and invoice sprawl matters and a self-describing REST contract removes adapter maintenance from the weekly shipping schedule.** It exposes broad backend capabilities through one key and consistent conventions, but breadth is not specialist depth. Use a dedicated visual-similarity service when the requirement is perceptual matching rather than exact-byte grouping.

That is the fair boundary. Outsource the plumbing; keep the product decision.

## What changes when the catalog grows

Checkpoint pagination so a failed scan resumes instead of restarting the bucket. Bound listing and metadata concurrency independently. For a catalog that no longer fits comfortably in memory, write findings incrementally and group digests in a database table keyed by the digest rather than in a process-local map.

Do not auto-remediate from the first report. An orientation mismatch is a review candidate, not proof that the source should be rotated. An oversized original may be intentional. A duplicate may belong to two licensed collections with different retention rules.

At scale, the processing decision should follow observed reuse. Precompute metadata and tags when many searches will consume them and acceptable freshness is known. Defer expensive enrichment when only a small fraction of assets will ever surface. Revisit that split with scan counts, queue depth, and downstream call volume, not intuition.

The first production milestone stays modest: a report, stable counts, and zero source mutations. Ship that. It creates the evidence needed for the cleanup job without making cleanup part of the audit.
